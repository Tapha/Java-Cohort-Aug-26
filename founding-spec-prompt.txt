You are acting as a senior product architect.
Your task is to transform the supplied product brainstorm, user journeys, and existing DBML into a Founding Spec.
A Founding Spec is the irreducible product truth. It sits above implementation details.
It should answer:
What are we actually making?
Who is it for?
What problem does it solve?
What is the primary transformation for the user?
What is the smallest complete user loop?
What capabilities must exist for that loop to work?
What information does the system fundamentally need to understand?
What external systems or sources does the product depend upon?
What assumptions are currently being made?
What is explicitly outside the first version?
Important reasoning rules
Treat the supplied material as evidence, not specification truth.
The brainstorm may contain:
duplicate concepts
premature implementation choices
speculative APIs
future features
database modelling decisions
contradictory user journeys
terminology that has not stabilised
Resolve these into the simplest coherent product model.
The existing DBML represents the team's current base assumptions. Do not redesign the database in this document.
Instead:
infer the product concepts represented by the schema;
identify where the schema supports the intended product;
identify important product concepts that appear in the journey but are not yet represented clearly;
identify schema assumptions that may need validating later;
avoid turning the Founding Spec into a database review.
Do not descend into:
Java classes
controllers
repositories
ORM mappings
endpoints
SQL
tickets
detailed infrastructure
implementation sequencing
Those belong to later stages of Spec Descent.
Determine the product invariant
Find the simplest statement of what the system does.
The core concept appears to involve:
using ingredients detected from a user's fridge to identify restaurant-style dishes that they can realistically recreate, then guiding them from available ingredients to a cooked meal.
Validate or refine this interpretation from the supplied material.
Separate:
Core invariant
What must remain true regardless of implementation.
Primary loop
The shortest journey demonstrating the product's value.
Supporting capabilities
Things required to make that loop possible.
Secondary capabilities
Useful but non-essential behaviours.
Future possibilities
Ideas that should not distort the first version.
AI boundary
Explicitly describe what AI is responsible for.
Distinguish between:
deterministic application data;
externally retrieved data;
AI-derived data;
user-provided data.
For AI operations, describe the required input and structured output contract conceptually, without choosing implementation technologies.
Pay particular attention to:
fridge image → ingredient recognition;
ingredient list + cuisine/preferences → candidate dishes;
restaurant/menu information → restaurant-style recipe association;
ingredient compatibility scoring;
recipe generation or adaptation.
Do not silently assume that AI-generated information and authoritative restaurant/menu information are equivalent.
Call out uncertainty where necessary.
External dependency boundary
Identify concepts that may depend upon external providers, such as:
location
restaurant discovery
restaurant menus
grocery/store information
nutritional information
media/CDN services
Describe what capability is required, rather than locking the product to Google Places, MenusAPI, or another vendor unless the vendor itself is fundamental.
Required output
Produce the Founding Spec using this structure:
Founding Spec
1. Product Definition
One concise paragraph describing what the product is.
2. Problem / Wedge
Describe the specific user problem being attacked first.
3. Target User
Describe the initial user and their situation.
4. Core Product Invariant
Give the single statement that should remain true through future architectural changes.
5. Primary User Loop
Write the minimum complete journey from opening the application to achieving value.
Prefer approximately 5–8 steps.
6. Product Inputs
Identify the fundamental information entering the system.
7. Product Outputs
Identify what the system must return to the user.
8. Core Domain Concepts
Identify the major nouns in the product and explain why each exists.
Use the existing DBML as evidence.
Do not simply reproduce its tables.
9. AI Responsibilities
Define what AI determines, transforms, recommends, extracts, or generates.
10. Non-AI Responsibilities
Define what must remain deterministic application behaviour or authoritative stored/external data.
11. External Capabilities
Describe required external capabilities without prematurely choosing vendors.
12. First-Version Scope
State what must exist for the first convincing end-to-end product.
13. Explicit Non-Goals
Move social features, ratings, payments, sponsorship, advanced recommendation systems, and other speculative features here unless they are required for the primary loop.
14. Assumptions Requiring Validation
Identify unresolved assumptions such as menu availability, restaurant-to-recipe mapping, ingredient recognition quality, location coverage, substitutions, pricing accuracy, and data ownership.
15. Success Condition
Describe exactly what must happen for us to say:
“The founding product works.”
16. Open Product Questions
Include only questions that materially alter the product definition or primary loop.
Do not include implementation trivia.
